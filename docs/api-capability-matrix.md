# API Capability Matrix — Piped backend

Verified 2026-11-18 against live public instances, cross-checked against the
Piped OpenAPI spec (`TeamPiped/OpenAPI`) and the Piped-child frontend source.
"Verified" means the endpoint was called on a live instance and the response
was inspected. Instance health changes daily; this matrix records both the
contract and the observed reality.

Caveats on the table below: every "yes" in the live-check column is a single
author-observed call on 2026-11-18, not a re-run or an ongoing guarantee —
time-stamped instance health goes stale within hours. Rows marked "no" were
NOT tested live; their details come from the frontend source and the OpenAPI
spec only, and must be treated as unverified until M1-B exercises them.

Auth model (from frontend source, useApi.js): token from `/login`, sent as
`Authorization: <token>` header, stored per instance in
`localStorage["authToken" + hash(instanceUrl)]`. Optional separate
authentication instance (`authInstance` + `auth_instance_url`). Clients must
scope tokens per instance and never send a token to an instance it was not
issued by (spec §10).

## `/streams/{videoId}` response model

Fields (healthy response): `dash` (MPD URL or null), `hls` (m3u8 URL or
null), `livestream`, `videoStreams[]` (url, format, quality, codec, mimeType,
itag, bitrate, width/height, fps, videoOnly, init/index ranges, audioTrack*),
`audioStreams[]`, `subtitles[]` (url, name, code, autoGenerated, mimeType —
TTML via the instance proxy), `chapters[]`, `previewFrames[]`,
`relatedStreams[]`, `proxyPrefix`, `lbryId`, `visibility`, `category`,
`license`.

Consequences for the clients:

1. `/streams` fails far more often than discovery endpoints. Error taxonomy
   (spec §10) must treat extraction failure (500 with JSON `message`) as a
   first-class, actionable state — "instance blocked, try another instance" —
   not a generic error.
2. Instance failover (P2 in spec) may need to be pulled forward for playback
   only: automatic retry of `/streams` on the user's configured fallback
   instance list. Decision for M1; must not transfer auth tokens (§10).
3. A degraded `/streams` can return `dash: null, hls: null` with only
   progressive 360p. Client-side DASH generation (src/utils/DashUtils.js)
   does NOT compensate here: `generate_adaptation_set` excludes muxed
   (progressive) streams, so a progressive-only response yields an empty MPD
   on any platform. Android and iOS therefore lose quality EQUALLY on this
   payload — both fall back to progressive 360p. The Android advantage (HLS
   or client-generated DASH) exists only when the response carries adaptive
   formats or manifest URLs. iOS fallback ordering: `hls` → HLS entries in
   videoStreams (LBRY) → progressive MP4 → actionable error. Documented
   limitation per spec §8.
4. Self-hosting the backend (supported upstream, docs.piped.video) would
   take the family off public-instance AVAILABILITY — but it does not fix
   extraction blocking: a self-hosted instance still asks YouTube from its
   own IP and can be bot-blocked the same way. Open question for the owner;
   decide after M1-A's playback feasibility results.
